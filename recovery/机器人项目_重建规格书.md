## 5.6 关键卡点定位（★★★）

# 第 8 部分：下次别再丢 —— 日志留存方案

## 8.1 问题根因

```
buddy-proxy ──► 转发 ──► CodeBuddy 上游
     │
     └─► 只记录【元数据】(17 字段)，不记录【请求体】(messages/tools)
          ├─ LiteLLM 也未开启 messages 记录
          ├─ CodeBuddy CLI 会话只在本地 .codebuddy/ ，不上云
          └─ 400 条上限滚动覆盖 → 旧的会话永久丢失
```

**三个叠加的失效点**：
1. **无请求体留存** → 拿不到对话与代码
2. **无云端副本** → CLI 会话只有本地一份
3. **滚动覆盖** → `proxy-usage.json` 只留 400 条，10-22 的记录被 11-02 之后的挤掉

## 8.2 立即可做的加固（三件事，1 小时内）

### 加固 1：buddy-proxy 加请求体落盘

**做法**：在 buddy-proxy 前面加一层轻量反向代理（nginx + lua，或一个 30 行 Python 服务），把 `POST /v1/chat/completions` 的请求体（含 messages）写入 JSONL。

**要点**：
- 只落 `messages` 和 `tools`，**不落 Authorization 头**
- 敏感信息（openid/手机号/密钥）需脱敏
- 按天分文件，保留 90 天
- **不影响现有转发链路**（失败时旁路放行）

### 加固 2：把 usage 的滚动上限改大 + 定期归档

`proxy-usage.json` 的 400 条上限是 buddy-proxy 的硬编码行为（Go 符号 `sessionpin.Table`）。**不可改**（闭源二进制），所以：
- 加 cron：每天把 `proxy-usage.json` 复制到 `/var/backups/buddy-usage/YYYY-MM-DD.json`
- 已备份：`/opt/buddy-stack/backups/buddy-data-*.tgz`（10-21、10-23 两份）
- **本次调查的关键数据就来自 10-23 那份备份** —— 证明这个方案有效

### 加固 3：给 liziy 的开发流程加一条规矩

> **凡是用反代 API 做的开发，必须同时保留：**
> 1. 源码目录的 git 远端（GitHub/Gitee 私有库）← **最重要**
> 2. `.codebuddy/projects/` 目录的定期同步（Windows 计划任务 → 云盘）
> 3. 关键对话的手动导出

## 8.3 建议的归档脚本

```bash
#!/usr/bin/env bash
# /opt/buddy-stack/scripts/archive-usage.sh
set -euo pipefail
DEST=/var/backups/buddy-usage/$(date +%Y-%m)
mkdir -p "$DEST"
cp /var/lib/docker/volumes/buddy-stack_buddy-data/_data/proxy-usage.json \
   "$DEST/usage-$(date +%Y%m%d-%H%M%S).json"
# 保留 90 天
find "$DEST" -name 'usage-*.json' -mtime +90 -delete
```
挂到 crontab 每日执行。
